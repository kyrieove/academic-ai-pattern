# AI-pattern 报告规范

报告是只读审查产物，不是改写后的稿件。

## 文件名

源文件为 `<stem>.<ext>` 时，报告写为同目录的 `<stem>-ai-pattern-report.md`。若已存在，依次使用 `-v2`、`-v3`。绝不覆盖旧报告。

## 必需章节与顺序

1. `## 审查元数据`
2. `## 执行摘要`
3. `## S1–S16 覆盖表`
4. `## 行动清单`
5. `## 发现`
6. `## 受保护与未触发模式`
7. `## 外部证据`
8. `## 限制`
9. `## 源文件校验`

即使没有发现也保留所有章节。

## 审查元数据

只记读者要用的四项：输入格式、作者模型、联网状态、提取警告。源文件名、模式、时间和规则版本写在标题行，不重复进表。不要写绝对路径。

模式写 `快速审查`、`深度审查` 或准确的聚焦范围。作者模型写 `稿件内生模型`、`§11 默认个人模型`、`补充样本`、`语料基线（作者 N 篇／领域 M 篇）`、`语料基线不覆盖` 或 `作者模型不足`。`语料基线不覆盖` 仅在存在基线且范围不匹配时使用；缺少已确认的作者偏好时，无论是否存在基线都可写 `作者模型不足`。

源文件 SHA-256 是校验用的，不是读的：写在文件末尾的 `## 源文件校验` 一节，不占开头的注意力。

## 覆盖表

列出 S1–S16。状态只用 `已审查`、`部分审查`、`未审查`。候选数为脚本候选与语义补充候选之和；执行摘要分别披露两者。原始候选 JSON 保留脚本计数。命中数不代表真实召回率。

`逐条裁决` 是该规则下写出了独立理由的裁决单元数。**它计的是执行程度，不是裁决结果**：`候选 68 / 逐条 8` 直接说明这条规则有 60 个候选没被单独判过。

**覆盖表不记裁决结果。** 每个候选的裁决保存在结构化账中；只有需要展开的问题进入 finding。`已审查` 要求全部候选有独立理由，且该规则已完成通读语义检查；未完成则标 `部分审查`。零命中不免除语义检查。

```markdown
| 规则 | 状态 | 候选数 | 逐条裁决 |
|---|---|---:|---:|
| S9 无根据的对立／幽灵反驳 | 已审查 | 0 | 0 |
```

聚焦审查必须把范围外规则标为 `未审查`，不能写成零命中。

## 行动清单

覆盖表之后、发现之前，一张表列出**全部** finding，含 `待作者判断` 与 `核查未完成`——清单的作用是这轮要处理的全集，漏掉后两类它们就会被忘掉。

一句话取该 finding 的 `处理方向` 首句：清单回答"我要做什么"，不是"为什么错"。

```markdown
| ID | 症状 | 裁决 | 位置 | 处理方向 |
|---|---|---|---|---|
| AP-S01-001 | S1 连续动词组／列表堆叠 | 需修改 | markdown-p0007 等 6 处 | 逐处砍掉不承载论证的项。 |
```

行数必须等于展开的 finding 数，由 `validate_report.py` 校验。

## Finding 类型与顺序

- AI 模式：`AP-S01-001` 至 `AP-S16-xxx`；
- 内容硬错误：`AP-H-001`；
- 方法学风险：`AP-M-001`。

同一个问题只展开一个主 finding，其他命中写入 `交叉规则`。

**排序：内容硬错误 → 方法学风险 → S1 至 S16。** 覆盖表、行动清单、发现区和账本四处同序，读者只需记住一套顺序。硬错误置顶是因为它们不是文风问题。

## 快速模式 finding

每项使用以下最小完整格式：

```markdown
### AP-H-001

**类别**：内容硬错误

**位置**：body-p0042

**触发片段**：

> Exact source sentence or shortest sufficient fragment.

**裁决**：需修改

**理由**：说明对象、方向、范围、证据或写作机制为何冲突。

**保护测试**：说明检查了什么合法功能，以及为何未受保护或为何受保护。

**证据**：稿内对应位置；必要时附外部来源及其支持边界。

**处理方向**：给出最小充分动作，不直接改稿。

**候选改法**：仅 `需修改` 可附，保留英文；不附时省略本字段。

**守恒核对**：附 `候选改法` 时必填。说明改法保持了哪些对象、方向、数量、范围、来源和证据等级；改动任一项时写明依据。

**交叉规则**：S11（如无则写“无”）

**账本**：S1-012345abcdef、S1-fedcba543210（本 finding 覆盖的裁决单元；如无则写“无”）
```

`位置` 必须使用提取 JSON 中的完整区块 ID，多个位置逐个写全，不省略前缀，以便验证每一段引文。

`触发片段` 必须逐字来自该区块；快速模式引用最短充分的完整句或短片段，不重复粘贴整段。跨句或分布问题可列多个区块，每段只引用建立问题所需的最短原文。

只有 `需修改` 可附一个 `**候选改法**`，其他裁决不给完整改写。附候选改法时必须同时写 `**守恒核对**`。守恒规则见 quick-rules.md「候选改法守恒」：候选改法中的事实、条件与论证关系都要能在触发片段或其所在区块指出依据，允许等义表达，不得新增人名、数字、日期、来源或因果，不得删除原有限定词与让步（S11 除外，且须写明依据）。

## 裁决账

正式验收使用 `<stem>-ai-pattern-ledger[-vN].json`；可另渲染同名 Markdown 供阅读，但 JSON 是计数与双向引用的唯一依据。原始脚本候选另存 `<stem>-ai-pattern-candidates[-vN].json`，保留扫描器输出，不手改计数或 ID。三个产物使用同一未占用版本，均不得覆盖。

```json
{
  "source_sha256": "与提取 JSON 相同的 SHA-256",
  "semantic_review": {"S1": true, "S2": false},
  "semantic_candidates": [
    {"id": "S10-MAN-001", "rule": "S10", "block_id": "markdown-p0007+markdown-p0009",
     "text": "第一处原文 || 第二处原文", "signal": "两处是否指同一测量对象，需要对照操作定义"}
  ],
  "decisions": [
    {"candidate_id": "S10-MAN-001", "reason": "正文给出的操作定义不足以区分两处测量对象。",
     "verdict": "待作者判断", "finding_id": null}
  ]
}
```

- `semantic_review`：每条范围内规则记录布尔值。true 表示执行者声明已通读检查，脚本不证明其语义质量。
- 脚本候选 ID 由扫描器提供，格式 `S1-<12位摘要>`，不得重新编号。语义补充使用 `S10-MAN-001` 等 ID，原文逐字来自对应区块；跨段使用 `+` 和 ` || `。
- `decisions` 必须覆盖所有脚本及语义候选，每个恰好一次，理由具体到内容。不得用通用理由批量保护。尚未逐条处理的候选记 `待作者判断`，理由 `未逐条裁决`，覆盖状态只能为部分审查。
- `需修改` 必须有 `finding_id`。其他候选可用 null；需要作者行动时也可展开。
- finding 的 `**账本**` 字段写对应完整候选 ID，与 `finding_id` 双向对应，裁决一致。AP-H/AP-M 无 S 候选时写“无”。
- 引用文本、完整位置 ID 与原始扫描范围必须可核对；不能添加范围外候选。

## 深度模式增量

深度模式的每个 finding 仍保留上述字段，但 `触发片段` 改为完整原文段落；跨段或分布问题引用全部必要完整段落。另补充子型、逐项判定过程、上下文／分布证据、联网目的、检索式、来源层级、支持结论和不能支持的边界。

不得用省略号删掉被审查的原文，也不得在引文中加粗、纠错或插入标签。

## 受保护与未触发模式

按规则简要说明代表性保护原因或零发现原因。快速模式不必为低风险受保护项逐条引用或联网；高风险的引文、主张强度和术语身份若影响裁决，应进入 finding。深度模式可展开高风险受保护项。

## 外部证据

只记录实际进行的联网核查。每条写 finding ID、目的、检索式、来源链接／层级、支持内容和不能支持的内容。未联网时明确写 `未联网（裁决仅依赖稿内证据）`。

搜索命中量只能证明用法存在，不能证明事实或语义正确。不得声称未经来源支持的表达“在文献中常见”。

## 限制

写明未审查章节、提取失败、付费墙、无法核对的来源和作者模型限制。没有限制时也明确写“未发现影响本次范围的提取或证据限制”。

## 禁止项与终检

- 不给 AI 概率、检测器分数、总分或通过阈值；
- 不虚构事实、数字、例子、文献或作者意图；
- 不把个人偏好伪装成通用错误；
- 不在任何必需步骤未完成时声称完整覆盖。

以下是反向终检，防的是改过头，逐项复查：

- 有没有只凭形式命中就定罪的 finding？保护测试必须写出这一句删掉后丢失的具体内容，写不出就降为 `待作者判断`；
- 有没有用同一条通用理由覆盖多个裁决单元？
- 候选改法里有没有触发片段和所在区块都不能支持的事实、机制、数字、日期或来源？
- 候选改法里有没有删掉原文的限定词、让步或范围限定？（S11 除外，且须在守恒核对写明依据）
- 有没有为"节奏""参差度""句长分布"建立 finding 或提出改法？句长离散度不是判据；
- 有没有把被动语态、名词化、长句、三项并列或句内同构排比本身当作 finding 依据？

交付前运行 `python scripts/validate_report.py report.md extract.json --source manuscript.docx --candidates candidates.json --ledger ledger.json`。自动重扫并核对原始候选清单，检查格式、占位符、原文溯源、数字 token、候选完整性、计数和双向引用。语义守恒、理由质量与引文支持关系必须另行人工／Agent 复核，不得把脚本通过称为语义正确性证明。
